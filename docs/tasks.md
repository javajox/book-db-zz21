Stage 3 evidence: `TextNormalizer` and `KeywordNormalizer` live in `domain.text` rather than in the application layer, because persistence stores comparison keys and must compute them identically; placing them in `application` would require persistence to depend upwards. `TextNormalizer` applies NFC, collapses whitespace runs, and trims, then derives a comparison key by lowercasing with `Locale.ROOT` and composing again. Two choices are deliberate and tested: whitespace is matched with `\p{IsWhite_Space}` rather than `\s`, because `String.strip` and `\s` both ignore a non-breaking space and would let one pasted name become a second author record; and length limits count code points rather than UTF-16 units, which both admits astral characters correctly and matches SQLite's `length()` for the CHECK constraints planned in stage 6.

`AttributeValidator` holds the individual rules and `BookAttributeValidator` applies them to a whole submission. Failures accumulate on a `FieldErrors` collector and are raised as one `ValidationException`, so a submission with eight bad fields reports all eight on the first save. A `collect` entry point accumulates onto a caller's collector so stage 4's ISBN rules and the services' reference checks report alongside attribute problems rather than in a second round. Text is normalized before its length is checked, so a padded value whose stored form fits is accepted. `ValidatedBookAttributes` is the proof that validation ran and cannot be constructed without at least one author and a positive print length; it deliberately omits ISBN values, since their checksums and canonical identity belong to stage 4. Field names are reported using the public JSON attribute names, held once in `FieldNames`.

- [x] **4.6** Implement the title fragment for book IDs: lowercase, normalize accented letters to ASCII where possible, replace runs of non-ASCII-letter/digit characters with a hyphen, trim boundary hyphens, truncate to 12 characters, remove any new trailing hyphen, and fall back to `book` when empty.
- [x] **4.7** Generate exactly six independently random lowercase ASCII letters or digits and append them with one hyphen. Produce complete IDs of 8–19 characters and keep suffix generation replaceable in tests so collisions can be reproduced reliably.
- [x] **4.8** Test valid/invalid ISBNs, leading zeros, `X`, equivalent ISBN pairs, mismatched pairs, and `979` values. Test metadata equality for reordered authors and absent values, and inequality for distinct editions, languages, or publishers.
- [x] **4.9** Test book-ID character rules, short/long/accented titles, punctuation, non-Latin titles, truncation boundaries, fallback behavior, and suffix length. Reserve database collision retry and ID immutability verification for the transactional services in stage 10.

Completion criterion: ISBN identities, duplicate metadata, and generated book IDs have deterministic validation and tested behavior.

Stage 4 evidence: `Isbn`, `IsbnIdentity`, `CanonicalMetadata`, `BookIdentity`, and `BookIdGenerator` live in `domain.identity`, alongside `domain.text` and for the same reason: the canonical ISBN identity and the canonical metadata key are stored columns with unique constraints, so persistence must derive them exactly as services do.

`IsbnIdentity` separates the two public ISBN attributes from the internal identity. Each public component holds exactly what the operator supplied and stays `NULL` when they supplied nothing, while `canonicalIsbn13` is always an ISBN-13 whenever any ISBN was given — which is what stops an ISBN-10 entry from sidestepping a stored book that already holds the equivalent ISBN-13. Absence never matches absence, since many books may legitimately have no ISBN; those are separated by metadata instead. Normalization also strips non-ASCII dashes, because an ISBN pasted from a web page commonly carries en-dashes.

The canonical metadata key writes every variable-length component as a length, a colon, and the content. Without that prefix the title `A|B` in English and the title `A` in language `B|English` would flatten to the same string, and a database unique constraint would reject one of two genuinely different books — reachable by an operator typing nothing more exotic than a punctuation mark. Author identifiers are sorted only for encoding, so the domain keeps them unordered; absent editions and publishers use an explicit marker that cannot collide with a positive value; and the key carries a version tag so stored keys can be migrated if the encoding ever changes.

`BookIdGenerator` takes its suffix source as a constructor argument. Stage 10 must prove that a generated-identifier collision is retried, and with real randomness that path needs a one-in-two-billion coincidence to trigger, so the seam is a requirement rather than a convenience.

`./gradlew clean build -Pvaadin.productionMode=true` passes with 271 executed tests, up from 148. Two claims were verified independently of the code under test: 200,000 randomly generated ISBN cases agreed exactly with a separate checksum implementation written from the ISBN rules, covering both check digits, validity, rejection of corrupted check digits, and ISBN-10 to ISBN-13 round trips; and 18,928 metadata tuples drawn from an adversarial component space — titles and languages containing `|` and `:` and length-prefix lookalikes such as `1:a`, plus author sets `{1,23}`, `{12,3}`, and `{123}` — produced 18,928 distinct keys with no collisions.

Stage 5 evidence: `DatabaseProperties` binds the two settings with constructor binding, so a configuration file, `BOOKDB_DATABASE_*` environment variables, and `--bookdb.database.*` command-line arguments all work; each mechanism has its own test. The documented busy-timeout range is 100 ms to 60 000 ms — below the floor a routine write collision would fail rather than wait, and beyond the ceiling a blocked request outlives any sensible client timeout. Values outside it are rejected rather than clamped, because an operator who mistyped a timeout must not end up running with settings they never chose.

`DatabaseLocation` resolves the path against the working directory, creates the data directory when absent, and refuses a directory, a non-regular file, an unwritable file, and an unwritable directory. Writability is confirmed by creating and removing a real probe file, since `Files.isWritable` can disagree with the filesystem. The target is inspected before the directory is probed, so a path that exists but is the wrong kind of thing is reported as such instead of being blamed on its parent. Every failure aborts startup through `DatabaseConfigurationException`, which is deliberately outside the `ApplicationException` hierarchy: those errors describe a failed request and carry a message safe to show a user, while this one describes an unviable deployment and names the exact path.

Foreign keys, WAL, and the busy timeout are set through `SQLiteConfig` so the driver applies them as it opens each connection; SQLite resets `foreign_keys` per connection, so configuring it once at startup would leave every later connection unenforced. `DatabaseLifecycle` reads all three pragmas back and fails startup if any did not take effect, because `SQLiteConfig` expresses requests rather than guarantees and SQLite silently falls back to another journal mode when WAL cannot engage. On shutdown it checkpoints the write-ahead log, so a file left behind by a clean stop is complete and the offline-backup procedure in stage 17 is trustworthy. There is no connection pool: `SQLiteDataSource` opens a connection per operation against a local file, which for a single-operator database is a better trade than a dependency plus a shutdown-ordering problem, and it means no connection outlives its unit of work.

Migration is wired explicitly rather than through autoconfiguration, because Spring Boot 4 moved Flyway autoconfiguration into a separate `spring-boot-flyway` module that this classpath does not include — relying on it would have meant migrations silently never running, with the application starting against an empty database and failing at the first query. `SchemaMigration` migrates in its constructor and the `JdbcTemplate` bean takes it as a parameter, so the container, not a convention, prevents the stage 7 repositories from querying an unmigrated schema. `failOnMissingLocations` is false while `db/migration` does not yet exist; stage 6 should set it true so a JAR packaged without migrations fails loudly.

Stage 6 evidence: `V1__create_schema.sql` creates `publishers`, `authors`, `books`, and `book_authors` with lowercase, underscore-separated names throughout, and its header documents which columns are public attributes and which are internal.

Two representation decisions were forced by SQLite. Decimal kilograms are stored as `weight_grams INTEGER`: SQLite has no decimal type and `REAL` is binary floating point, so 0.544 kg could not be stored and returned unchanged, while three decimal places of a kilogram is exactly whole grams. **This deviates from the specification's attribute table, which names the column `weight`** — the column is named for its unit so that no reader mistakes grams for kilograms, and the JSON contract is unaffected because the API still exposes `weight` in kilograms. Dates are stored as ISO text validated by `CHECK (date(publication_date) IS publication_date)`; SQLite rolls an impossible day over to the following month rather than rejecting it, so comparing `date()`'s result with the stored text is what refuses `2026-02-30`, along with unpadded and non-ISO forms. `date(NULL)` is `NULL`, so an absent date satisfies the check without a separate branch.

Four internal columns carry identity: `normalized_title` for search, `canonical_isbn_13` for edition identity, `canonical_metadata_key` for the duplicate-book rule, and `normalized_name` on authors and publishers. The metadata key cannot be a generated column, because it depends on the `book_authors` rows that SQLite cannot see from a column expression; services compute it with `domain.identity` and write it in the same transaction as the record. A `CHECK` ties `canonical_isbn_13` to the presence of a supplied ISBN, so no row can carry an ISBN that uniqueness never examines. Unique constraints cover both supplied ISBN forms, the canonical identity, and the metadata key; SQLite treats NULLs as distinct, so any number of books may have no ISBN. Deletion rules are asymmetric on purpose: `ON DELETE CASCADE` from `book_authors` to `books` removes a deleted book's links, while `ON DELETE RESTRICT` to `authors` and from `books` to `publishers` means removing a reusable record can never silently strip a book of an author or a publisher.

Several SQLite behaviours were confirmed before being relied on: `length()` counts characters rather than bytes, which makes the schema's limits agree with the code-point counting chosen in stage 3; `GLOB` with a negated class enforces the generated identifier form; and `trim()` does not strip a non-breaking space, so the blankness checks are defence in depth behind service normalization rather than a complete guard. Three rules are deliberately left to other layers and recorded as such in the migration header: at-least-one-author, which no table constraint can express; real image decoding; and full Unicode blankness.

Stage 7 evidence: `AuthorRepository` and `PublisherRepository` share `NormalizedNameRepository`, since the two differ only in their table, their length limit, and how "still referenced" is determined. Two copies of insert, fetch, rename, search and delete would drift, and the half that drifted would be the half deciding whether two spellings are the same person. Generated identifiers come from `INSERT ... RETURNING id`: the data source is unpooled, so each `JdbcTemplate` call opens its own connection and `last_insert_rowid()` asked separately reports zero — the trap stage 6 hit first.

`BookRepository` keeps brief and full reads as separate paths. A brief read selects three book columns plus author names and never mentions `cover_image`, so the books list and `/books-brief` do not pull every stored cover through the driver to display titles. Author names for a whole result set are fetched in one query rather than per book, which keeps a fifty-book list at two round trips instead of fifty-one. Author and publisher names are always joined from their own tables rather than copied into the book row, so a rename appears on every linked book with no further work; this is verified for both. The identifier is absent from the update statement's `SET` list, so no ordinary update can change it however a caller is written. Multi-query reads need a caller-provided transaction to see one snapshot, which the repository documents and stage 11 will supply, since repositories do not open transactions.

Search accepts one field and matches four things: exact identifier, partial normalized title, partial normalized author name, and an ISBN in either form resolved through the canonical identity, so an ISBN-10 from a book jacket finds a record stored with only its ISBN-13. `LikePatterns` escapes `%`, `_` and the escape character itself before building a `LIKE` pattern, with the escape declared in the SQL: an operator searching for `100%` means a title containing "100%", and without escaping both that search and a search for `_` would silently return the wrong rows rather than failing visibly. All supplied values are bound as parameters.

Weight conversion uses `RoundingMode.UNNECESSARY` deliberately. Validation has already confirmed at most three decimal places, so a value needing rounding here means an unvalidated weight reached the repository, and failing loudly beats storing a number nobody entered. Reading back strips trailing zeros, so 500 grams returns 0.5 rather than 0.500.

`ValidatedBookAttributes` moved from `application.validation` to `domain` as part of this stage. The repositories consume it, and leaving it in the application layer would have made `persistence` depend upwards.

Stage 9 evidence: `CoverImageValidator` takes bytes and nothing else — no filename, no browser-supplied content type — so there is no declared label to be wrong about. The media type stored beside the image is the one a decoder recognized, which makes the `content-type` the API reports a fact about the file rather than a claim about it. A declared type is consequently never a reason to reject: a PNG arriving as `cover.jpg` is stored as the PNG it is, while a text file renamed `cover.png` is rejected for not decoding.

The dimensions are read from the header before any pixels are touched, and the bound is far beyond any plausible book cover. **And `MemoryCacheImageInputStream` rather than `ImageIO.createImageInputStream`**, which was verified to return a `FileCacheImageInputStream` and write every upload into `java.io.tmpdir`; that would have contradicted the requirement that cover handling creates no image files outside SQLite, and a test now points ImageIO's cache at a directory it controls and asserts it stays empty.

`PendingCover` holds a form's intent in memory: keep by default so editing a page count cannot clear a cover, with replace and remove as explicit choices. It validates on upload rather than at save time, so an unusable file is reported while the operator still has it in front of them; a rejected save leaves the pending image untouched, and a failed second upload does not destroy an already-chosen valid one. `reset` is what Cancel calls. Nothing is written anywhere until the book is saved, so an abandoned form is just a dropped object.

The guarantee that matters most is that the application cannot start unsecured. `SecurityProperties` requires an operator username, a BCrypt password hash and the SHA-256 digest of the API token, and rejects a missing, blank or wrong-shaped value with a message naming the provisioning command. There is no built-in account and no fallback, because a deployment that refuses to start is a problem someone fixes in a minute while one that starts with anonymous management access is a problem nobody notices. It prompts for the password rather than accepting it as an argument, since an argument is visible to every process listing and lands in shell history.

The two audiences get opposite treatment on purpose. The API chain matches only the two read paths, holds no session, compares token digests with `MessageDigest.isEqual` so the comparison does not reveal how much of a guess was right, and answers an unauthenticated read with HTTP `401` and the `unauthorized` JSON error — never a redirect, because a consumer following one would receive HTML with a success status and could not tell it from data. That response is now part of the API contract in the specification, as stage 1 required. The GUI chain uses Vaadin's `VaadinSecurityConfigurer`; route access is annotation-based, with `@AnonymousAllowed` on the login view alone, so a new view with no annotation fails closed rather than being published. CSRF protection is disabled on the API chain only, where there is no session or cookie to forge with, and left intact for the GUI.
